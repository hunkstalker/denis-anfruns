Aquí es donde mucha gente se pierde. Empezamos a ver `<T>`, `interface`, `type`, `return T`... todo mezclado y parece jeroglífico.

Vamos a desenredarlo paso a paso.

## Generics en Interfaces vs Tipos

¿Cuándo usar uno u otro? La sintaxis es casi idéntica.

<CodeTabs items={[
    {
		label: 'TypeScript',
		code: `// Opción A: Interface Genérica
interface CajaInterface<T> {
    valor: T;
}

// Opción B: Type Genérico
type CajaType<T> = {
    valor: T;
};

// Se usan IGUAL
const a: CajaInterface<string> = { valor: "Hola" };
const b: CajaType<string> = { valor: "Hola" };`,
		lang: 'typescript'
    }
]} />

No hay diferencia funcional real para datos simples. Usemos la que prefiramos (solemos usar `interface` para objetos y `type` para funciones/uniones).

## El Patrón "Wrapper" (Datawrapper)

Este es el caso de uso #1 en el mundo real: Respuestas de API.
Tenemos una estructura fija (`data`, `status`, `error`) pero el contenido de `data` cambia según la llamada.

<CodeTabs items={[
    {
		label: 'TypeScript',
		code: `// Definamos la "cáscara" genérica
interface ApiResponse<Data> {
    status: number;
    message: string;
    data: Data; // 👈 Aquí va la magia
}

// Definamos nuestros modelos concretos
interface User { id: number; name: string; }
interface Product { sku: string; price: number; }

// ¡Combinémoslos!
type UserResponse = ApiResponse<User>;
type ProductResponse = ApiResponse<Product>;

function fetchUser(): UserResponse {
    return {
        status: 200,
        message: "OK",
        data: { id: 1, name: "BartoloDev" } // TS sabe que data es User
    };
}`,
		lang: 'typescript'
    }
]} />

## "Prop Drilling" de Tipos

A veces tenemos Generics dentro de Generics. Es como pasar una variable de un abuelo a un nieto.

<CodeTabs items={[
    {
		label: 'TypeScript',
		code: `interface PaginatedResponse<T> {
    items: T[];       // Array de T
    total: number;
    page: number;
}

// ApiResponse contiene PaginatedResponse, que contiene User
type UsersApi = ApiResponse<PaginatedResponse<User>>;

// Parece complejo, pero TS lo resuelve solo:
// UsersApi = { 
//   status: number,
//   message: string,
//   data: { 
//      items: User[], 
//      total: number,
//      page: number,
//   } 
// }`,
		lang: 'typescript'
    }
]} />

## Avanzado: `infer` (Funciones de Tipos)

Esto ya es nivel cinturón negro, pero solo para que sepas que existe.
Puedes crear un Tipo que "extraiga" tipos de otros tipos usando `infer`.

<CodeTabs items={[
    {
		label: 'TypeScript',
		code: `// Un tipo que extrae el tipo de dentro de un Array
type UnpackArray<T> = T extends (infer U)[] ? U : T;

type StringArray = string[];
type JustString = UnpackArray<StringArray>; 
// Resultado: string`,
		lang: 'typescript'
    }
]} />

<Callout type="warning" title="Insight: Funciones de Tipos">
¿Te das cuenta de lo que acabamos de hacer? `UnpackArray<T>` es literalmente una función.
Recibe un argumento (`T`).
Hace un `if` (`extends`).
Devuelve un resultado (`U` o `T`).

¡El sistema de tipos de TypeScript ES un lenguaje de programación en sí mismo! 🤯
</Callout>

<Callout type="tip" title="¿Por qué UnpackArray devuelve string?">
**Explicación detallada de `infer U`**:
Cuando escribimos `T extends (infer U)[]`, le estamos preguntando a TS: *"¿El tipo T se parece a un Array de algo? Si es así, captura ese 'algo' y llámalo U"*.

1. Pasamos `string[]` como `T`.
2. TS compara `string[]` contra `(infer U)[]`.
3. Deduce que `U` debe ser `string`.
4. Devuelve `U` (`string`).
</Callout>

## Generics en Funciones Flecha

La sintaxis aquí puede llegar a asustar, especialmente en archivos `.tsx` (React) y donde se vuelve más complejo.

<CodeTabs items={[

// Función flecha

// ⚠️ En archivos .tsx (React), necesitamos una coma para que no crea que es HTML
